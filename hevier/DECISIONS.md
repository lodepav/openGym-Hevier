## Routine editor

Added 2026-10-16, at the start of M3.

| # | Decision |
|---|---|
| D15 | **Hevy's table over openGym's plan, not per-set plans.** An openGym routine exercise is one prescription (`sets × reps @ weight`, a warm-up count, back-off, an intensifier, "last set to failure"), and the progression engine moves it as one. Only a pyramid has per-set reps and weights. So the routine editor draws Hevy's SET · KG · REPS table *from* that prescription: a flat exercise's rows share one weight and one rep target (typing in any row changes them all), back-off rows show their derived weights read-only, a double/triple-progression exercise shows **REP RANGE** (`8–12`, tap to edit), and only a pyramid's rows are edited one by one. Set types map to what the plan can hold: **W** = the warm-up count (weights are worked out at session start), **F** = "last set to failure" (the last set only; a pyramid's is **Max**), drop sets / rest-pause / back-off / pyramid / per side / progression stay in upstream's exercise settings behind ⋮ → **Settings & progression** (D8). Edits save as they are made, as upstream's editor does: the header has **Done**, not Cancel / Save. Exercises are **reordered by a long press** on their header (changed 2026-10-18, at the user's request: it was a handle, kept for keyboards only); a superset moves as one (upstream's `reorderRoutineUnit`). Routine-wide Progression, Deload and the body map stay below the exercises. |

## Backup to Google Drive

Added 2026-10-17, at the user's choice.

| # | Decision |
|---|---|
| D20 | **Google Drive through a sync app, no fork code.** Upstream's auto-backup (Settings → Data & backup → **Auto-backup on changes**) already writes the whole of `S` after a workout or an edit, one dated file a day, the newest 14 kept, into `Documents/openGym/` or a folder picked with the system picker (#161). A sync app on the phone (Autosync for Google Drive, FolderSync, …) mirrors that folder to Drive. The fork builds no Drive client: a Google sign-in, an OAuth client and a Play Services dependency would go against upstream's "no third-party account" and dependency-light rules, and be native code to carry across merges. Restore is upstream's **Import backup** (a replace; signed in, it offers **Merge them in** when the server has workouts the backup lacks). Everything that must be in the backup therefore lives in `S` (RULES.md, "Every change"), not in `localStorage`. |

## Security gates

Added 2026-10-17, at the user's choice.

| # | Decision |
|---|---|
| D26 | **Release builds pass three local gates, and a failure blocks.** `hevier/tools/release-check.sh` (also the `release-check` skill, and `verify` before a release) builds the mobile bundle and runs: **secrets** (gitleaks over the whole git history, the built bundle, and an APK when given), **vulnerable dependencies** (Trivy over all four npm lockfiles, dev dependencies included, every severity, and the APK's Java libraries: added 2026-10-18, after the review, `hevier.gradle` locks the debug and release runtime classpaths into `frontend/android/app/src/hevier/gradle.lockfile`, so a build whose libraries differ from the lock fails until it is written again and its diff read) and **supply chain** (`hevier/tools/supply-chain.mjs`: every npm package pinned by a lockfile must be in a reviewed baseline, come from the npm registry and carry an integrity hash, so a new or bumped package or a new install script fails until it is read and accepted; and the built JS may name only allow-listed hosts and holds no `eval`, `new Function`, long base64 or escaped blobs, WebSocket, `sendBeacon` or `importScripts` unless listed). Any finding fails. An exception is an entry in a fork-owned allow-list under `hevier/security/` with its reason (Trivy's also scoped to the package version and expiring), so accepting one is a reviewed diff. Local only, no CI: the fork builds its APK on the developer's machine. The scanners are pinned binaries installed user-local with checksums (`hevier/tools/install-scanners.sh`), not npm dependencies and not Docker. APK checks (permissions, debuggable, signing certificate) were left out at first; D38 adds them. The vulnerability gate prints the age of Trivy's database and fails when it is more than a week old (added 2026-10-18, after the review). **The gates run at the same time** (added 2026-10-20, at the user's request): the ones that read only the sources start before the bundle is built, each into its own log, printed in order, about 10 s in place of 40; the release tools' own tests (`release-notes.mjs`, `supply-chain.mjs`) are a gate too, and the release script runs them before it numbers a release. Upstream files are not touched. |

## Hevy import

Added 2026-10-17, at the user's choices, after the user's own Hevy export was
run through upstream's matcher and every match was checked against its catalogue artwork.

| # | Decision |
|---|---|
